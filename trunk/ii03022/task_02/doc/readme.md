## 1. Цель работы

Освоить технологию модульного (юнит-) тестирования программ на C++ с применением
фреймворка **Google Test**: научиться проверять правильность отдельных единиц
кода, строить параметризованные тесты, работать с граничными случаями,
измерять тестовое покрытие и трактовать его результаты. Дополнительно —
закрепить навыки ООП (наследование, виртуальные методы, выделение модулей) на
примере программы лабораторной работы №1.

## 2. Постановка задачи

Объект тестирования — программа ЛР1 (папка `trunk/ii03022/task_01/`):
три модели (1.8 линейная, 2.2 с насыщением, 3.6 кубическая), раздельные входные
воздействия (ступень, импульс, гармоника), анализ устойчивости модели 1.8.

Требования (по методичке):

1. покрыть программу модульными тестами с помощью Google Test, запуск — через
   CMake/ctest (bat-файл);
2. проверить **правильность вычислений** на наборах параметров, пересчитанных
   вручную;
3. проверить **анализ устойчивости**: `true` на устойчивых коэффициентах,
   `false` на расходящихся, а также **граничные случаи** (корень строго на
   окружности $|z| = 1$);
4. проверить **граничные значения нелинейности** (точки $u_{min}$, $u_{max}$,
   сигнал внутри и вне зоны насыщения);
5. применить **параметризованные тесты** (`TEST_P`/п.8 методички) там, где
   один и тот же сценарий гоняется по таблице данных;
6. обеспечить **разные режимы входных воздействий** (п.9): без Google Mock —
   подменой входных сигналов фиксированными последовательностями;
7. в отчёте отразить **процент тестового покрытия** (file/line coverage).

## 5. Тестовые сценарии и ручной пересчёт

Все эталонные значения в тестах получены ручным расчётом по формулам моделей
(полные развёртки — в файле `paper_check.md`, ниже — основные).

### 5.1. Правильность значений (траектории)

**Модель 1.8**, $y_{t+1} = a_1 y_t + a_2 y_{t-1} + b_1 u_t + b_2 u_{t-1}$,
коэффициенты $\{0.5;\ 0.3;\ 1;\ 0.5\}$, ступень $u = 1$:

$$y_0 = 0 + 0 + 1 \cdot 1 + 0 = 1.0 \qquad
y_1 = 0.5 \cdot 1 + 0 + 1 + 0.5 = 2.0 \qquad
y_2 = 0.5 \cdot 2 + 0.3 \cdot 1 + 1 + 0.5 = 2.8$$

Траектория $1.0 \to 2.0 \to 2.8$ и записана в таблицу теста. Аналогично
посчитаны импульс на неустойчивом наборе ($1.0 \to 1.7 \to 2.34$) и гармоника
($u_t = \sin t$: $0;\ 0.841470985;\ 0.909297427$ — синус **в радианах**).

**Модель 2.2**, $y_{t+1} = a y_t + b\,\mathrm{sat}(u_t)$, $a = 0.5$, $b = 1$,
границы $\pm 2$, ступень амплитудой 5 (режется до 2):

$$y_0 = 0 + \mathrm{sat}(5) = 2.0 \qquad
y_1 = 0.5 \cdot 2 + 2 = 3.0 \qquad
y_2 = 0.5 \cdot 3 + 2 = 3.5$$

**Модель 3.6**, схема Эйлера $y_{t+1} = y_t + h\,(a y_t^3 + b u_t)$,
$a = -0.5$, $b = 1$, $h = 0.05$, ступень $u = 2$:

$$y_0 = 0 + 0.05 \cdot 2 = 0.1 \qquad
y_1 = 0.1 + 0.05 \cdot (2 - 0.0005) = 0.199975 \qquad
y_2 = 0.199975 + 0.05 \cdot 1.9960015 \approx 0.299775$$

**Инвариант покоя** проверен для всех трёх моделей: нулевой вход при нулевом
состоянии даёт $y \equiv 0$ (система без возбуждения покоится).

### 5.2. Анализ устойчивости

Характеристическое уравнение $z^2 - a_1 z - a_2 = 0$; система устойчива тогда и
только тогда, когда **оба** корня строго внутри единичного круга.
Проверяемая таблица (8 наборов — `TEST_P`):

| $a_1$ | $a_2$ | Корни | Вердикт |
|:--:|:--:|---|:--:|
| 0.5 | 0.3 | $z_1 = 0.8521$, $z_2 = -0.3521$ | STABLE |
| 0.9 | 0.05 | действительные, оба $< 1$ | STABLE |
| 0.5 | −0.5 | $0.25 \pm j0.6614$, $\|z\| = \sqrt{0.5} = 0.7071$ | STABLE |
| 1.2 | 0.3 | $z_1 = 1.4124$ | UNSTABLE |
| 0.5 | −1.2 | комплексные, $\|z\| = \sqrt{1.2} = 1.095$ | UNSTABLE |
| 1.0 | 0.0 | $z_1 = 1$ — **ровно на окружности** | UNSTABLE |
| 0.5 | 0.5 | $z_1 = 1$ — граница | UNSTABLE |
| 0.0 | −1.0 | комплексные, $\|z\| = 1$ — граница | UNSTABLE |

Граничные строки доказывают, что сравнение в коде должно быть **строгим**
`< 1.0`, а не `<= 1.0`. Отдельные тесты проверяют: числовые значения корней
(с точностью `1e-6`), ветку комплексной пары в печати, наличие слова `WARNING`
в отчёте при неустойчивости и его отсутствие при устойчивом наборе.

> Ручная проверка первой строки: $D = 0.25 + 1.2 = 1.45$, $\sqrt D = 1.2041595$, $z_{1,2} = (0.5 \pm 1.2041595)/2 = 0.8520797;\ -0.3520797$ — оба меньше 1 ✔.
> Это те же корни, что печатались в отчёте ЛР1.

### 5.3. Границы нелинейности (модель 2.2)

Параметризованная таблица покрывает все положения входа относительно зоны
насыщения: выше $u_{max}$ (5 → 2), ниже $u_{min}$ (−100 → −2), внутри зоны
(ограничитель не вмешивается: $1.5 \to 0.25 \to 1.625$), ровно точки
$u = u_{max}$ и $u = u_{min}$ (границы **включены**: $\mathrm{sat}(2) = 2$).
Отдельный тест `SaturatorClampsExactly` при $a = 0$ превращает модель в чистый
ограничитель ($y = \mathrm{sat}(u)$) и проверяет все пять случаев напрямую.

### 5.4. Инварианты и сверка с аналитикой (модель 3.6)

1. **Равновесие:** при $a < 0$ и постоянном $u$ система сходится к точке
   $\bar y = \sqrt[3]{-bu/a} = \sqrt[3]{4} \approx 1.5874$; симуляция (40 шагов)
   даёт 1.5853 — разница < 0.005.
2. **Эйлер vs точное решение:** для $\dot y = -y^3$, $y(0) = 1$ точное
   решение $y(t) = 1/\sqrt{1 + 2t}$; после 100 шагов с $h = 0.01$ численное
   значение $0.5758$ против аналитического $1/\sqrt 3 \approx 0.57735$
   (допуск 0.01). Так проверяется, что схема Эйлера решает именно то уравнение.
3. **`reset()`** возвращает модель в начальное условие $y_0$ (для 3.6 — не в
   ноль, а в параметр конструктора): после «разгона» состояния и сброса ответы
   совпадают со свежесозданным объектом.

### 5.5. Входные сигналы

Ступень (константа $A$ на всех тактах), импульс ($A$ только на $t = 0$),
гармоника ($A\sin t$: $\sin 1 = 0.841470985$), неизвестный тип → 0
(сигнал «молчит», программа не падает).

### 5.6. Почему без мок-объектов (п.9)

Google Mock не подключался: мок нужен для подмены **внешних зависимостей**
(файлы, сеть, БД), а у наших классов их нет — входом метода `nextStep(u)`
является число, выходом — return-значение. Вместо моков использованы ручные
подмены (stub-приёмы):

- модели в тестах питаются **фиксированными последовательностями** `u[]`,
  записанными в таблицу, — заодно так легко подать все три режима (ступень,
  импульс, гармоника);
- `printStabilityReport(a1, a2, out)` печатает **в параметр-поток**: в `main` это
  `std::cout`, в тесте — `std::ostringstream`, который можно проверить.

Проверяется результат (state-based testing), а не взаимодействие — mock-фреймворк
здесь избыточен.

## 7. Тестовое покрытие

Измерение: `gcov`/`gcovr` (MinGW GCC, флаги `-O0 --coverage`), учитываются
модули `src/`. **Важный момент методики:** интерактивный `main.cpp` в замер
**не входит** (исключён флагом `--exclude ".*main\.cpp"`) — это обвязка
ввода-вывода с меню, а не unit-логика; без исключения его 87 невыполненных
строк дают обманчивые «47 %», хотя все тестируемые модули при этом покрыты на
100 %.

| Модуль | Строки | Функции | Комментарий |
|---|:--:|:--:|---|
| `Model 1.8.h` | 100 % (14/14) | 100 % | вся рекуррентная формула + `reset()` |
| `Model 2.2.h` | 100 % (13/13) | 100 % | включая обе ветки ограничителя `sat()` |
| `Model 3.6.h` | 100 % (10/10) | 100 % | Эйлер + ветка конструктора с `y0` |
| `StabilityAnalyzer.h` | 100 % (33/33) | 100 % | обе ветки дискриминанта, оба исхода |
| `InputSignal.h` | 100 % (6/6) | 100 % | все `case` + ветка по умолчанию |
| `Model.h` | 100 % (1/1) | 100 % | тело виртуального деструктора |
| **Итого** | **100 % (77/77)** | **100 % (15/15)** | **Success** |

Сноски:
- счёт строк у gcov зависит от версии GCC на единицу-две: например GCC 14.2
  считает в `Model 1.8.h` 12 строк вместо 14 и помечает неисполнимую строку
  объявления `nextStep() = 0` в `Model.h` — тогда итог по строкам выглядит как
  98.7 % (75/76). В обоих случаях **исполняемый код покрыт полностью**;
  покрытие функций стабильно 100 % (15/15).
- метрика `branches` заданием не нормируется и в отчёт не заносится.

Команда замера (после прогона `run_tests.bat`, из папки `task_02`):
