Освоить технологию модульного (юнит-) тестирования программ на C++ с применением фреймворка **Google Test**: научиться проверять правильность отдельных единиц кода, строить параметризованные тесты, работать с граничными случаями, измерять тестовое покрытие и трактовать его результаты. ## 2. Постановка задачи

Объект тестирования — программа ЛР1: три модели (1.3 линейная, 2.10 нелинейная (tanh), 3.2 кубическая), раздельные входные воздействия, анализ устойчивости модели 1.3.

Требования:
1. покрыть программу модульными тестами с помощью Google Test, запуск — через CMake/ctest (bat-файл);
2. проверить **правильность вычислений** на наборах параметров, пересчитанных вручную;
3. проверить **анализ устойчивости**: `true` на устойчивых коэффициентах, `false` на расходящихся, а также **граничные случаи** (корень на окружности \(|z| = 1\));
4. проверить **граничные значения нелинейности**;
5. применить **параметризованные тесты** (`TEST_P`);
6. обеспечить **разные режимы входных воздействий** подменой входных сигналов;
7. в отчёте отразить **процент тестового покрытия**.

## 5. Тестовые сценарии и ручной пересчёт

Все эталонные значения в тестах получены ручным расчётом по формулам моделей.

### 5.1. Правильность значений (траектории)

**Модель 1.3**, \(y_{t+1} = a_1 y_t + a_2 y_{t-1} + b u_t\), коэффициенты \(\{0.5;\ 0.1;\ 1.0\}\), ступень \(u = 1\):
* \(y_1 = 0.5 \cdot 0 + 0.1 \cdot 0 + 1.0 \cdot 1 = 1.0\)
* \(y_2 = 0.5 \cdot 1.0 + 0.1 \cdot 0 + 1.0 \cdot 1 = 1.5\)
* \(y_3 = 0.5 \cdot 1.5 + 0.1 \cdot 1.0 + 1.0 \cdot 1 = 1.85\)

**Модель 2.10**, \(y_{t+1} = a \tanh(y_t) + b u_t^3\), \(a = 1.0\), \(b = 1.0\). При \(u = 10\) (проверка границ):
* \(y_1 = 1.0 \cdot \tanh(0) + 1.0 \cdot 10^3 = 1000.0\)

**Модель 3.2**, метод Эйлера \(y_{t+1} = y_t + dt \cdot (b u_t)\), \(b = 2.0\), \(dt = 0.1\), ступень \(u = 1.0\):
* Аналитическое решение: \(y(t) = b \cdot u \cdot t = 2.0 \cdot t\).
* На 6-м шаге (\(t = 0.6\)): \(y_6 = 2.0 \cdot 0.6 = 1.2\).

### 5.2. Анализ устойчивости

Характеристическое уравнение \(z^2 - a_1 z - a_2 = 0\). Система устойчива, если оба корня строго внутри единичного круга (\(|z| < 1\)).

| \(a_1\) | \(a_2\) | Корни | Вердикт |
|:--:|:--:|---|:--:|
| 0.5 | 0.2 | действительные, оба \(< 1\) | STABLE |
| 1.0 | −0.5 | действительные, оба \(< 1\) | STABLE |
| 2.0 | 0.0 | \(z_1 = 2\) | UNSTABLE |
| 0.0 | −1.0 | \(z_{1,2} = \pm j\), \(|z| = 1\) (граница) | UNSTABLE |

Граничные строки доказывают, что сравнение в коде должно быть **строгим** (`< 1.0`), а не `<= 1.0`.

### 5.3. Границы нелинейности (модель 2.10)

Модель проверяется на нулевой вход (зона нечувствительности) и на больших значениях \(u\) (проверка функции \(\tanh\) и куба).
Отдельный тест проверяет, что при \(u=0\) и нулевом начальном состоянии система находится в покое (\(y=0\)).

### 5.4. Инварианты и сверка с аналитикой

1. **Инвариант покоя:** нулевой вход при нулевом состоянии даёт \(y \equiv 0\) для всех трёх моделей.
2. **Эйлер vs точное решение:** для \(\dot y = bu\) численное интегрирование сравнивается с линейной аналитикой (см. п. 5.1).
3. **`reset()`** возвращает модель в начальное нулевое состояние. В тестах вызывается после "разгона" состояния.

### 5.5. Почему без мок-объектов

Вместо моков использованы ручные подмены (stub-приёмы): модели в тестах питаются **фиксированными последовательностями** `u[]`, записанными в таблицу параметризованных тестов. Это позволяет легко подать все три режима (ступень, импульс, гармоника) без дублирования кода.
